# GitHub API Bulk Operation Limits — Issue Creation, Labeling, Commenting at 50–150 Volume

Research date: 2026-10-22. Scope: a single authenticated personal account (classic/fine-grained PAT, `gh auth login`), no GitHub App, no OAuth App installation. Target workload: create ~50–150 issues, then repeatedly read/label/comment on all of them (feasibility-check agent + report-generator agent).

## Executive Summary (copy-pasteable)

- **You will not hit primary rate limits.** Personal-account REST and GraphQL primary limits are **5,000 requests/points per hour** each ([REST limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [GraphQL limits](https://docs.github.com/en/graphql/overview/rate-limits-and-node-limits-for-the-graphql-api)). 150 issues × (1 create + 1 label + 1 comment) ≈ 450 REST calls — under 10% of the hourly budget.
- **Secondary (abuse) rate limits are the real constraint.** GitHub caps content-creating requests (issue/comment/label create, etc.) at **no more than 80/minute and 500/hour**, concurrency at **≤100 concurrent requests**, and per-endpoint traffic at **≤900 points/min (REST)** or **≤2,000 points/min (GraphQL)** ([best practices — secondary rate limits](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)).
- **Concrete batching cadence: serialize requests, 1 request at a time, with a minimum 1-second sleep between each `POST`/`PATCH`/`PUT`/`DELETE`.** This is GitHub's own explicit guidance ("wait at least one second between each" mutating request) and, at ~60/min, keeps you safely under the 80/min content-creation ceiling even with jitter/retries ([best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)).
- **Always create every label before applying any label to an issue.** `POST /issues/{n}/labels` 404s if a named label doesn't already exist in the repo — there is no auto-create-on-apply behavior. Pre-create the full label set once at the start of the run, then apply.
- **Retry/backoff is the caller's job — `gh` and the REST/GraphQL APIs do not auto-retry.** Check `Retry-After` first; if absent, check `x-ratelimit-remaining == 0` and sleep until `x-ratelimit-reset`; otherwise back off exponentially starting at ~60s ([best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)).
- **Use REST (`gh issue create/edit/comment`) for writes at this scale, GraphQL for bulk reads.** 50–150 writes don't benefit from GraphQL's node-based batching (no supported way to batch independent mutations safely in one call that lowers effective cost), but the **report-generator agent should read via `gh api graphql --paginate`** to pull issues+labels+comments in a handful of requests instead of one REST call per issue.
- **Pagination:** REST pages max at 100 items/page (`gh api --paginate` follows `Link` headers automatically); GraphQL connections use cursor pagination (`first`, `after`, `pageInfo.hasNextPage/endCursor`) and `gh api graphql --paginate --slurp` ([gh_api manual](https://cli.github.com/manual/gh_api)). `gh issue list` defaults to `--limit 30` — pass `--limit 150` (or higher) explicitly to get the full set in one call.

## 1. Primary rate limits (REST and GraphQL) at this volume

- **REST, authenticated personal token:** "All of these requests count towards your personal rate limit of 5,000 requests per hour." Tracked via response headers `x-ratelimit-limit`, `x-ratelimit-remaining`, `x-ratelimit-reset` (UTC epoch seconds). Source: [Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).
- **GraphQL, authenticated personal account:** primary limit is **5,000 points/hour** (Enterprise Cloud org members get 10,000/hour — not applicable here). Query point cost is computed from connection sizes (sum requests needed for every connection traversed — assuming `first`/`last` limits are hit — divide by 100, round to nearest whole number). Node limit: **individual calls cannot request more than 500,000 total nodes.** Source: [Rate limits and node limits for the GraphQL API](https://docs.github.com/en/graphql/overview/rate-limits-and-node-limits-for-the-graphql-api).
- **Issue creation / label creation / label application / comment creation** are all ordinary authenticated REST calls and each consumes 1 of the 5,000/hour primary budget — e.g. creating 150 issues, creating ~10 labels, applying labels to 150 issues, and posting 150 comments is on the order of 450–460 calls, well inside the primary budget regardless of whether it's done in one run or split across several.
- **Reading/listing issues** (`GET /repos/{owner}/{repo}/issues`, or `gh issue list`) is also 1 REST call per page; with a 100-items-per-page cap, reading 150 issues takes only 2 pages = 2 calls.
- Net: **primary limits are not the binding constraint for 50–150 issues** — secondary limits (below) are.

## 2. Secondary (abuse) rate limits

Per GitHub's best-practices doc ([Best practices for using the REST API](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)):

- **Concurrency:** "No more than 100 concurrent requests are allowed," shared across REST and GraphQL.
- **Content creation:** "In general, no more than 80 content-generating requests per minute and no more than 500 content-generating requests per hour are allowed." This explicitly covers issue/comment/label creation via REST, GraphQL, *and* the web UI combined.
- **Per-endpoint request volume:** "No more than 900 points per minute are allowed for REST API endpoints, and no more than 2,000 points per minute are allowed for the GraphQL API endpoint."
- **Serialization guidance:** "To avoid exceeding secondary rate limits, you should make requests serially instead of concurrently... implement a queue system for requests." And: **"If you are making a large number of `POST`, `PATCH`, `PUT`, or `DELETE` requests, wait at least one second between each request."**
- **Backoff on 403/429 with secondary limit error:** "If the `retry-after` response header is present, you should not retry your request until after that many seconds has elapsed." If `x-ratelimit-remaining` is `0`, wait until `x-ratelimit-reset`. "Otherwise, wait for at least one minute before retrying. If your request continues to fail due to a secondary rate limit, wait for an exponentially increasing amount of time between retries, and throw an error after a specific number of retries."

**Implication for this workload:** creating 150 issues + applying labels to 150 issues + posting 150 comments = ~450 content-creating requests. At the mandated 1-request/second serialized cadence (≈60/min), that's **~7.5 minutes** of steady runtime and stays safely under both the 80/min and 500/hour content-creation ceilings. Running faster than ~70–75/min risks tripping the secondary limit even though you're nowhere near the primary 5,000/hour cap.

## 3. Does GraphQL beat REST at 50–150 writes?

- GraphQL's **primary** rate cost model is built for query-shaped connection traversal (nested `first`/`last` pagination), not for counting discrete mutations — the docs describe mutation cost for the **secondary** limit only: "GraphQL requests with mutations" are weighted **5 points** vs **1 point** for mutation-free queries, measured against the 2,000-points/minute per-endpoint secondary ceiling ([GraphQL rate limits](https://docs.github.com/en/graphql/overview/rate-limits-and-node-limits-for-the-graphql-api)).
- The GraphQL docs and schema reference do **not** document a supported way to send multiple independent mutations (e.g., several `addComment`s for different issues) in a single request and have them count as one cheaper unit — each mutation field in a request is still a distinct operation and is each charged the mutation weight; there's no bulk/batch mutation primitive for issues/labels/comments in the public schema.
- **Net at 50–150 writes: no meaningful advantage to GraphQL mutations over REST.** The per-request overhead difference is irrelevant at this volume, REST's `gh issue create/edit/comment` wrappers are simpler to script and already handle JSON/field mapping, and GraphQL mutations still hit the same 1-request-per-second secondary-limit serialization requirement.
- **GraphQL *does* help for reads.** A single GraphQL query can fetch an issue's number, title, state, labels, and comments together via nested connections, replacing 2–3 REST calls (issue + labels + comments) per issue. For the **report-generator agent** reading 150 issues, this cuts total requests roughly 2–3x and is well within the `500,000` node cap and the 5,000-points/hour primary budget. Use `gh api graphql` with a paginated `issues(first: 100, after: $cursor)` connection.
- `gh api graphql` is **easier** than hand-rolled REST pagination for the read path (one query, nested data, built-in `--paginate`/`--slurp` support per the `gh api` manual below) but **harder/no-better** than `gh issue create`/`gh issue edit`/`gh issue comment` for the write path, since those subcommands already wrap the REST calls with sane defaults, templating, and `--body-file` support.

## 4. Pagination / batching patterns

- **REST via `gh api --paginate`:** "all pages of results will sequentially be requested until there are no more pages of results," following the response's `Link` header automatically ([gh_api manual](https://cli.github.com/manual/gh_api)). REST list endpoints cap at **100 items per page** (standard GitHub REST convention; request with `per_page=100` to minimize call count). Combine with `--jq` to filter/project fields from each page inline, and `--cache <duration>` (e.g. `--cache 1h`) to avoid repeat reads burning primary-limit budget during iterative script development.
- **GraphQL via `gh api graphql`:** cursor-based pagination — the query must accept `$endCursor: String`, fetch `pageInfo { hasNextPage endCursor }` on the connection, and `gh api graphql --paginate` drives the cursor loop; add `--slurp` to merge all pages into one JSON array for downstream `jq` processing ([gh_api manual](https://cli.github.com/manual/gh_api)).
- **`gh issue list`:** defaults to `--limit 30` and open issues only (`--state open` default) — for a 50–150 issue run you must pass `--limit 150` (or more) and `--state all` explicitly, or it silently truncates/filters. There is no separate `--page`/`--offset` flag; `--limit` is the only sizing control and `gh` paginates under the hood up to that limit ([gh_issue_list manual](https://cli.github.com/manual/gh_issue_list)).
- **Recommended batching pattern for this workload:** list/read in as few large-page calls as possible (2 REST pages of 100, or 1–2 GraphQL pages of 100), but **serialize writes one at a time with the mandated ~1 second spacing** — reads and writes should not be parallelized against each other given the shared 100-concurrent-request ceiling and the lower content-creation ceiling.

## 5. Concrete gotchas for scripted bulk label/comment operations

- **Labels must exist before they can be applied.** `POST /repos/{owner}/{repo}/issues/{issue_number}/labels` ("Add labels to an issue") operates on label *names* but does not auto-create missing labels; community reports and labeler-tool documentation consistently show a **404 "Label does not exist"** error when a referenced label name hasn't been created via `POST /repos/{owner}/{repo}/labels` first ([Labels API reference](https://docs.github.com/en/rest/issues/labels); corroborating real-world behavior: [github/issue-labeler#20](https://github.com/github/issue-labeler/issues/20), [actions/labeler#807](https://github.com/actions/labeler/issues/807)). **Action: enumerate and `gh label create` (or REST `POST .../labels`) every distinct label up front, before the first `gh issue edit --add-label` call.** `gh label create` only creates one label per invocation and has no bulk mode, and fails outright (unless `--force`) if the label already exists — so pre-check or guard with `--force` to make the pre-creation step idempotent across reruns ([gh_label_create manual](https://cli.github.com/manual/gh_label_create)).
- **Label application supports batching per issue, not across issues.** Both `POST .../issues/{n}/labels` (append) and `PUT .../issues/{n}/labels` (replace) accept an **array** of label names in one request, so apply all labels for a single issue in one call — but there's no endpoint to apply labels to multiple *issues* in one call; that still requires one request per issue ([Labels API reference](https://docs.github.com/en/rest/issues/labels)).
- **Labeling + commenting in the same burst compounds secondary-limit exposure.** If the feasibility-check agent does `create label (once) → add labels to issue → post comment` per issue in a tight loop, that's 2 content-creating requests per issue beyond the one-time label setup — at 150 issues that's 300 content-creating requests; interleave the mandatory 1-second spacing *between every one* of these calls, not just between issues, since both label-apply and comment-create separately count against the shared 80/min content-creation ceiling.
- **Neither `gh` nor the REST/GraphQL APIs retry automatically.** The `gh_api` manual documents no built-in retry/backoff for rate-limit responses — the script/skill must inspect `retry-after` / `x-ratelimit-remaining` / `x-ratelimit-reset` itself and sleep accordingly, per GitHub's own guidance ([best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)). Plan for this explicitly in the skill's implementation (wrap each `gh` invocation with a retry helper), it is not free.
- **`--recover` exists for `gh issue create`** to resume a failed/aborted creation from a saved draft — useful if a bulk-create run is interrupted partway through, but it's a single-issue recovery mechanism, not a batch-resume feature; the calling script still needs to track which of the 50–150 issues were successfully created (e.g., record returned issue numbers to a local file) so a rerun doesn't duplicate issues.
- **Attachments are independently fallible:** `gh issue create --attach` uploads up to 50 files per invocation but documents that "if some attachments upload and others fail, the issue is still created with the ones that succeeded," exiting non-zero — don't assume a non-zero exit means no issue was created; check for a created issue number before treating it as a failure to retry ([gh_issue_create manual](https://cli.github.com/manual/gh_issue_create)).

## 6. Concrete, actionable recommendation

For a script/skill creating 50–150 issues and later reading/labeling/commenting on all of them with one personal PAT:

1. **Pre-flight:** enumerate every distinct label the run will need; `gh label create <name> --color <hex> --force` for each, once, before any issue work starts (idempotent via `--force`).
2. **Create phase:** loop `gh issue create` one at a time; after each call, `sleep 1` (minimum) before the next create/label/comment call of any kind. Track each created issue's number in a local manifest file as you go, so a crashed/interrupted run can resume without duplicating issues.
3. **Label/comment phase (feasibility-check agent):** for each issue, do `gh issue edit <n> --add-label "a,b,c"` (one call applies all labels for that issue) then `gh issue comment <n> --body-file ...`; insert `sleep 1` between every individual mutating call (label-apply and comment are each counted separately against the 80/min content-creation ceiling), not just between issues. At 150 issues × 2 mutating calls each + ~10 label creates ≈ 310 calls × 1s ≈ **5–6 minutes** of serialized runtime — well under both the 500/hour content-creation cap and the 5,000/hour primary cap.
4. **Backoff on failure:** before every mutating call, if the previous response carried `retry-after`, sleep that many seconds; else if `x-ratelimit-remaining == 0`, sleep until `x-ratelimit-reset`; else on a secondary-limit error (HTTP 403/429 with the abuse-rate-limit message), start at 60s and double on each consecutive failure, capping retries (e.g., 5 attempts) before surfacing an error.
5. **Never parallelize writes.** Keep concurrency at 1 for all create/label/comment calls — GitHub explicitly recommends serial requests over concurrent ones to avoid secondary limits, and the 100-concurrent-request ceiling is a hard cap shared across REST+GraphQL that provides no real headroom benefit at this content-creation-gated volume anyway.
6. **Report-generator agent (read-only, run repeatedly):** use `gh api graphql --paginate --slurp` with a query over `repository.issues(first: 100, after: $endCursor) { nodes { number title state labels(first: 20){nodes{name}} comments(first: 50){nodes{body createdAt}} } pageInfo { hasNextPage endCursor } }` — this pulls issues + labels + comments together in ~2 GraphQL calls for 150 issues instead of 300–450 separate REST calls, and stays far under both the 5,000-points/hour primary budget and the 500,000-node-per-call limit. No special backoff cadence is needed for pure reads since they're not subject to the content-creation ceiling, but still respect `x-ratelimit-remaining`/`retry-after` defensively.
7. **Use REST (`gh issue create/edit/comment`), not GraphQL, for the write path** — GraphQL mutations offer no batching or cost advantage at 50–150 writes and add scripting complexity versus the purpose-built `gh` subcommands.
